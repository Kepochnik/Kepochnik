# BOUNCER · limitations

- **Snipe tax shape.** The factory publishes the start tax and the window; the decay curve is inside the bonding-curve contract. The slip shows the terms and what each buy in the window actually paid (from the curve's own `CurveBuy` event), not a predicted tax for a buy at second N. If the curve reports the door tax outside the `tax` field of `CurveBuy`, the "paid at the door" column would understate it; run `bouncer door` on a fresh launch and compare with the explorer before quoting a number.
- **Launch search window.** The launch block is found by walking factory logs backwards, 7 days by default. Older launches get "launch older than the search window" instead of a cover charge section. Pass `--launch-blocks` (CLI) to widen it.
- **Public RPC.** `rpc.mainnet.chain.robinhood.com` rate-limits bursts and caps the block span of `eth_getLogs`; the client paces requests and halves chunk sizes on range errors. A chunk that fails at the minimum size is an error, never a gap. Browser use of the public endpoint depends on its CORS policy; the site lets you paste another endpoint and stores it only in your browser.
- **Bytecode scan.** Opcodes are counted outside PUSH immediates and the metadata trailer. A contract that hides data sections after `INVALID` (as factories embedding creation code do) can produce false positives; that is why the scan is a `WATCH` on registered Pons launches and a `STOP` only on unknown addresses.
- **Proxies.** Only EIP-1967 (implementation and beacon slots) and EIP-1167 are recognised. A hand-rolled proxy shows up as `DELEGATECALL` instead.
- **Dev report card.** Counts launches by deployer address only. A deployer that rotates wallets gets a clean card; that is the one-crew problem, planned as a later feature via funding-source clustering, which needs an indexer.
- **Pool exit estimates.** The graduated-pool exit door models the locked full-range position from PoolManager storage and prices the sale with the hook's live policy. Extra LPs, concentrated positions and any hook logic beyond a fee (the Pons hook also runs buyback) are not modelled; the number is an estimate and the slip says so. HOP OUT's pool-depth method is the reference for anything finer.
- **Funding sources.** ONE CREW sees native transfers Blockscout indexes as transactions to the wallet. A wallet funded by an ERC-20 transfer, a contract call or an internal transaction shows "not found" and counts as unresolved. Exchange hot wallets fund many unrelated users; a shared funder is a fact to read, not a verdict.
- **Lookalikes** depend on the explorer's search index, which can lag a fresh launch by a few blocks; the subject is always included.
- **Arc.** The Arc testnet entry is from Radian's published deployment; Arc mainnet has no factory or explorer in the table until Radian publishes them. Live reads on Arc were not run from the machine this was built on; the demo chain and the tests exercise the same code paths.
- **Watch is polling, not a subscription.** Events are read from logs between the last cursor and the head; a very short window can miss nothing but a reorg can reorder blocks. The bot keeps watches in memory unless `BOUNCER_STATE_FILE` is set; the site tab stops when closed.
- **The board's cover read is chain-wide.** One hour of `CurveBuy` logs on Robinhood Chain is tens of thousands of logs; the adaptive reader halves chunks on range errors but the public RPC may still take a minute. `--no-cover` keeps the deployer board alone, which is cheap. Pass `--hours` sparingly.
- **MCP server.** Speaks the stdio transport (one JSON-RPC message per line) with `initialize`, `ping`, `tools/list` and `tools/call`; no resources, prompts, sampling or streamable HTTP. Any client that runs stdio servers can use it.
- **Pons V1.** On Robinhood Chain a token missing from the V2 factory is looked up in the V1 factory (`PonsLaunchFactory`, `0xA5aAb3F0c6EeadF30Ef1D3Eb997108E976351feB`) and, when the token's own `launchFactory()` names it, in the older deployment `0x0c37a24F5D23A486FA692d1500881d698B1F77a4` (the one that made $PONS). A V1 token is on the list with V1 rules (Uniswap V3 pool from block one, launch caps, locked position, graduation status) plus the open-door facts; the V2 sections (door tax, curve exit, room, crew) do not apply and are not shown. V1 dev history is not read. Other V1 factory deployments, if any exist, are read only once added to the chain table.
- **Open door: names, not proofs.** The function surface is read from pushed four-byte constants, which is what compilers emit for dispatchers; a contract assembled by hand or one that dispatches through a lookup table can hide a function from this read. Whether a listed function is guarded by an owner, a role or nothing at all is not readable from bytecode, so the slip says the code carries a switch and states separately what is readable about ownership. The verified-source flag says whether anyone can read the rest.
- **The sale simulation proves one unit, at one block.** `eth_call` of `transfer(pool, 1)` from a real holder shows that the token does not refuse that transfer right now. It does not price the trade, so a fee on transfer, a sell tax, a maximum sale size, a per-wallet cooldown and slippage are all invisible to it. It does not run inside a real transaction, so a contract that checks `gasleft()`, the block number, the caller's history or the transaction's origin can pass it and still trap a buyer. It is a snapshot: an owner who flips a blacklist or raises the sell tax after the slip is printed makes it obsolete, which is why the powers list sits next to it. A pool-directed probe is only run when a pool with liquidity was found on the chain's DEX table, so a token trading somewhere else gets the wallet-to-wallet answer alone, labelled as such.
- **Reads that fail say so.** Every probe has three outcomes and a rate-limited or unreachable endpoint produces "not run", never "reverts". The same rule holds for `owner()`, for `totalSupply()` and for the explorer: an unread supply makes every share `unknown` rather than `0.0%`, and the concentration warnings do not fire on an unknown share. The cost is that a busy endpoint yields a thinner slip; the alternative was a confident wrong one.
- **Open door: explorer data.** Holders, deployer, creation, recent transfers, the price feed and the scam flag come from Blockscout, not the chain; balances that matter (deployer, owner, pools) are re-read from the chain. Without an explorer the open door still reads the code, the owner, the switches and the pools, and skips the rest with a note. Blockscout puts a bot challenge in front of clients without a browser-like user agent; the CLI, the bot and the proxy send one, browsers send their own.
- **Pools.** Only V3-style factories in the chain table are asked (`getPool` at the four standard fee tiers, paired with WETH). Pools against other pairs, V2-style pairs, Uniswap V4 pools (which $PONS itself trades in, through the PoolManager) and other DEXes (Ramses on Robinhood Chain, for one) do not show up here; the holder list often shows them as named contracts. Reserves are balances, not in-range liquidity. Whether the liquidity is locked is not read at all.
- **EIP-7702 wallets.** Blockscout reports an account that signed a delegation as a contract. BOUNCER reads its `proxy_type` and counts it as a wallet, so concentration among real holders is not understated and such a wallet can be sampled for the simulation. An explorer that does not return that field would put those wallets back in the contract bucket.
- **Demo mode and real addresses.** The demo chain knows only its invented addresses. The site switches to live by itself when a real address is pasted in demo mode; the CLI needs `--demo` dropped.
- **Not an audit, not advice.** The slip says what is true at the block on the stamp. It does not say what happens next.
